# Phase 0 Research: R0 Agent Fleet Control Plane Walking Skeleton

## 1. Application Shape

**Decision**: Use a pnpm TypeScript workspace containing a React/Vite web app, one NestJS/Fastify modular API that can also run its PostgreSQL worker, shared contract/database packages, and a minimal workspace connector.

**Rationale**: This preserves the modular-monolith deployment and transaction boundary while allowing the environment-side connector to run where the workspace and VPN exist. Shared packages keep API, UI, connector, and tests aligned without sharing module-owned persistence code.

**Alternatives considered**: Microservices were rejected by the constitution. A single process on the workspace host was rejected because control-plane deployment and environment placement differ. No connector was rejected because every self-hosted session needs an executor inside the workspace.

## 2. Backend Framework

**Decision**: Use NestJS with its Fastify adapter.

**Rationale**: Nest modules, providers, guards, and test utilities fit the required domain boundaries. Fastify supplies a lean HTTP runtime, while Nest has first-class SSE handlers and lifecycle cleanup.

**Alternatives considered**: Bare Fastify would require custom module wiring. Express adds no advantage for this API and streaming workload.

**Sources**: [NestJS modules](https://docs.nestjs.com/modules), [NestJS server-sent events](https://docs.nestjs.com/techniques/server-sent-events)

## 3. Database and Migrations

**Decision**: Use PostgreSQL with Drizzle ORM and reviewed SQL migrations generated by Drizzle Kit.

**Rationale**: The model relies on JSONB snapshots, append-only event/audit tables, explicit constraints, partial indexes, and transactions. Drizzle keeps SQL behavior visible while providing typed schema declarations.

**Alternatives considered**: Prisma is capable, but its current migration generation is newer and less direct for this event-heavy PostgreSQL schema. Handwritten SQL alone would duplicate types and slow iteration.

**Sources**: [Drizzle migrations](https://orm.drizzle.team/docs/migrations), [Drizzle transactions](https://orm.drizzle.team/docs/transactions), [Drizzle indexes and constraints](https://orm.drizzle.team/docs/indexes-constraints)

## 4. OpenAI Execution Boundary

**Decision**: Use the OpenAI Agents API and official JavaScript SDK behind an `OpenAIAgentsGateway`. Pin the SDK version during implementation and isolate beta payload/event mappings in that adapter.

**Rationale**: OpenAI owns the agent harness and session protocol. ADLC owns local configuration, readiness, state, evidence, and projections. Adapter isolation protects domain modules from contract changes and enables fixture-based tests.

**Alternatives considered**: A custom harness violates the constitution. Browser-to-OpenAI calls would expose credentials and bypass persistence and redaction.

**Source**: [OpenAI Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview)

## 5. Self-Hosted Workspace Connection

**Decision**: Install one ADLC workspace connector in the configured workspace. For each session it launches the official `codex exec-server` using only the OpenAI-provided remote URL and environment ID, the approved workspace path, and a restricted executor key.

**Rationale**: OpenAI runs the harness, but the executor must run inside the customer environment and each session needs its own executor. A constrained connector gives the UI a real start-session flow without arbitrary shell execution or a custom runtime.

**Alternatives considered**: Manual executor startup fails the product-level golden path. A custom runtime is prohibited. An OpenAI-hosted environment cannot reach the required private workspace/VPN resources and is outside R0.

**Source**: [OpenAI self-hosted sandboxes](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted)

## 6. MCP Origin and Credentials

**Decision**: Configure the remote HTTP MCP with `connection_origin: "environment"`. Resolve its credential reference on the backend and supply session-scoped transport authentication without storing plaintext in definitions, snapshots, events, logs, or responses. Prefer a trusted proxy inside the VPN when credentials must be hidden from the execution environment.

**Rationale**: The DevOps MCP is reachable only through the workspace VPN. Environment-origin HTTP is designed for private networks. It does not use OpenAI vault credentials, so ADLC must use per-session authentication or a trusted proxy and redact before persistence.

**Alternatives considered**: Service-origin MCP cannot reach VPN-only endpoints. Stdio is unnecessary for an existing HTTP server. Persisted plaintext headers violate the constitution.

**Source**: [OpenAI MCP connections](https://developers.openai.com/api/docs/guides/agents-api/tools/mcp)

## 7. Skill Registration

**Decision**: Register an existing skill by OpenAI skill ID or source reference and version. Inline ZIP upload is out of scope. Resolve the active version and capability directory into the session configuration and snapshot.

**Rationale**: This matches the existing Capability Registry boundary and avoids adding package upload, scanning, storage, and distribution to the walking skeleton.

**Alternatives considered**: Inline ZIP upload is explicitly deferred. Embedding skill content in agent versions violates registration-by-reference.

## 8. Session Streaming and Idempotency

**Decision**: Persist upstream events first, assign a monotonic local sequence, normalize transactionally, and expose app-owned SSE using that sequence as the SSE `id`. Reconnect uses `Last-Event-ID` to replay stored events before live follow.

**Rationale**: Browser disconnects must not stop the upstream run or duplicate evidence. A unique `(session_id, source_event_id)` constraint prevents duplicate ingestion.

**Alternatives considered**: Direct stream proxying loses replay. WebSockets are unnecessary for one-way updates. Replaying all raw events for dashboard queries conflicts with the dashboard guidance.

## 9. Session Lifecycle

**Decision**: Use nonterminal states `creating`, `provisioning`, and `running`, followed by exactly one immutable terminal state: `completed`, `failed`, `canceled`, or `interrupted`. Confirmed executor or upstream loss without a terminal outcome becomes `interrupted`.

**Rationale**: This distinguishes user intent, execution failure, and infrastructure interruption while preserving partial evidence.

**Alternatives considered**: Mapping interruption to failure contradicts the clarification. `requires_action` is excluded because the acceptance agent uses Always allow and approval handling is deferred.

## 10. Artifact Identity and Validation

**Decision**: Treat each distinct artifact report event as one artifact record. Enforce uniqueness on the source report event, not file path. Store only a normalized workspace-relative `.md` path, status, provenance, and metadata; verify containment in the connector.

**Rationale**: This implements report-occurrence identity, prevents path traversal, and avoids copying file contents. Replayed events are idempotent, but genuine repeated reports remain distinct.

**Alternatives considered**: Global or per-session path identity contradicts the clarification. Copying content into PostgreSQL conflicts with the filesystem-reference boundary.

## 11. Test Strategy

**Decision**: Use Vitest, PostgreSQL Testcontainers, Playwright, protocol-faithful OpenAI/MCP fakes, and one opt-in live OpenAI smoke test.

**Rationale**: Most behavior stays deterministic while one live test verifies the beta external contract. Browser tests validate user-visible boundaries and navigation.

**Alternatives considered**: Live calls in the normal suite are costly and nondeterministic. Unit tests alone cannot prove transactions, replay, redaction, or the complete UI flow.

**Sources**: [Playwright](https://playwright.dev/), [Playwright best practices](https://playwright.dev/docs/best-practices)

## Research Outcome

All technical-context unknowns are resolved, and the design passes the constitution before Phase 1.
